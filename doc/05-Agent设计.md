# Agent 设计

## 1. 技术选型

Agent 编排使用 **LangGraph**，原因：

- 法律业务流程不是一次性问答，而是包含路由、检索、工具调用、风险判断、引用校验的多步骤状态流
- 不同 Agent（法律咨询、案例分析、合同审查）有不同的节点和边，LangGraph 的图结构天然支持
- 支持条件分支（如：检索结果不足 → 补充检索 → 再推理）
- 支持人工介入节点（如：合同审查高风险条款需人工确认）
- 内置 Checkpoint 支持对话暂停和恢复

## 2. 通用 Agent 状态图

所有 Agent 共享一个基础状态图，具体场景通过节点覆写实现差异化：

```text
                    START
                      ↓
              ┌─── Router ───┐
              │  (场景路由)    │
              └──────┬───────┘
                     ↓
              ┌── Intent ────┐
              │ (意图+领域分类)│
              └──────┬───────┘
                     ↓
              ┌── Retrieve ──┐
              │ (多路检索)    │
              └──────┬───────┘
                     ↓
              ┌─ Retrieve ───┐  ← 条件边
              │ Judge        │  (结果不足 → 补充检索)
              │ (检索质量判断) │
              └──────┬───────┘
                     ↓ (通过)
              ┌── Reason ────┐
              │ (推理+工具调用)│
              └──────┬───────┘
                     ↓
              ┌── Citation ──┐
              │ (引用构建+校验)│
              └──────┬───────┘
                     ↓
              ┌─ Validate ───┐  ← 条件边
              │ (回答质量校验)│  (引用失败 → 重新生成)
              └──────┬───────┘
                     ↓ (通过)
                    END
```

### 2.1 LangGraph 状态定义

```python
from typing import TypedDict, List, Optional, Annotated
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages

class LegalAgentState(TypedDict):
    # 输入
    query: str                          # 用户原始问题
    conversation_id: str                # 会话 ID
    kb_ids: List[str]                   # 可用知识库 ID 列表
    tenant_id: str                      # 租户 ID

    # 中间状态
    intent: str                         # 意图类型
    legal_domain: str                   # 法律领域
    rewritten_query: str                # 改写后的查询
    expanded_queries: List[str]         # 扩展查询列表
    retrieved_chunks: List[dict]        # 检索到的 Chunk
    retrieval_quality: str              # 检索质量: sufficient / insufficient
    reranked_chunks: List[dict]         # 重排后的 Chunk
    context: str                        # 压缩后的上下文

    # 对话历史
    messages: Annotated[List, add_messages]  # 对话消息

    # 法律特化
    legal_memory: dict                  # 法律上下文记忆
    citations: List[dict]               # 引用列表
    citation_validation: dict           # 引用校验结果

    # 输出
    answer: str                         # 最终回答
    needs_human_review: bool            # 是否需要人工审核
    risk_alerts: List[dict]             # 风险提醒（合同审查专用）
```

### 3.2 输出规范

法律咨询 Agent 必须覆盖以下内容，缺一不可：

```text
✅ 问题归类      — 属于哪个法律领域
✅ 法律依据      — 具体的法律条款和内容
✅ 分析过程      — 从法律到事实的逻辑推理
✅ 风险提示      — 可能的例外、限制、实务风险
✅ 引用来源      — 可点击追溯的法条原文
⚠ 免责声明      — "本分析仅供参考，不构成法律意见"
```

### 4.2 合同审查 Prompt 模板

```text
## System Prompt: 合同审查 Agent

你是一位资深商事律师，专注于合同审查。你的任务是审查用户提供的合同条款，
识别法律风险，并提供具体的修改建议。

### 审查维度
1. **合法性**: 条款是否违反法律强制性规定
2. **公平性**: 条款是否显失公平，权利义务是否对等
3. **完整性**: 是否缺少必备条款
4. **明确性**: 条款表述是否清晰，是否存在歧义
5. **可操作性**: 条款在实务中是否可执行

### 风险等级定义
- 🔴 **高风险**: 违反法律强制性规定，或可能导致重大损失
- 🟡 **中风险**: 对一方明显不利，或存在法律争议
- 🟢 **低风险**: 表述不够完善，但不会导致重大不利后果

### 输出要求
对于每个风险条款，输出：
1. 原文引用
2. 风险等级和类型
3. 法律依据（必须引用具体法条）
4. 修改建议（原文 → 建议修改后的文本）
5. 修改理由

### 约束
- 引用法条必须是真实存在的，不确定的法条不要引用
- 不确定的问题应建议咨询专业律师
- 不要在缺乏依据的情况下做出确定性的法律结论
```

## 8. Memory 管理：法律上下文记忆

### 8.1 法律 Memory 结构

法律对话的 Memory 需要维护比普通对话更丰富的上下文：

```python
class LegalMemory:
    """法律对话上下文记忆"""

    # 对话中的法律话题追踪
    current_law: str          # 当前讨论的法律（如"民法典"）
    current_article: str      # 当前讨论的法条（如"第585条"）
    current_topic: str        # 当前讨论的主题（如"违约金调整"）

    # 法律概念追踪
    mentioned_laws: List[str]      # 对话中提到的所有法律
    mentioned_articles: List[str]  # 对话中引用的所有法条
    mentioned_cases: List[str]     # 对话中提及的案例

    # 事实上下文
    user_facts: dict          # 用户提供的案件事实
    # 例如: {"role": "出租人", "合同类型": "商铺租赁", "争议金额": "50万"}

    # 引用一致性
    citation_history: List[dict]
    # 追踪每轮引用的法条，确保跨轮次引用一致
```

### 8.2 跨轮次引用示例

```text
第1轮:
  用户: "我租的房子漏水，房东不管怎么办？"
  Agent: "根据《民法典》第712条，出租人应当履行租赁物的维修义务..."
  Memory 更新:
    current_law = "民法典"
    current_article = "第712条"
    current_topic = "出租人维修义务"
    user_facts = {"role": "承租人", "contract_type": "房屋租赁"}

第2轮:
  用户: "那如果我要自己修呢？" ← 口语化，省略主语和背景
  Agent:
    1. 从 Memory 恢复上下文: 房屋租赁 + 维修问题
    2. 关联法条: 第712条 → 第713条（自行维修的后果）
    "根据刚才讨论的《民法典》第713条，您在通知房东后如果房东不维修，
     您可以自行维修，维修费用由房东承担..."
  Memory 更新:
    current_article = "第713条"
    maintained: current_law = "民法典", user_facts

第3轮:
  用户: "我修了花了5000块，怎么要回来？"
  Agent: Memory 已有完整上下文 → 直接引用第713条 + 补充费用追偿程序
```

### 8.3 Memory 压缩策略

长对话中，将历史记忆压缩为摘要：

```text
原始 Memory (10轮对话后膨胀):
  messages: [msg1, msg2, ..., msg20]  ← 可能超出 LLM 上下文窗口

压缩后:
  summary: "用户为房屋承租人，租赁的房屋存在漏水问题。
            第一轮确认了出租人的维修义务(民法典第712条)；
            第二轮讨论了承租人自行维修后的费用追偿(第713条)；
            第三轮涉及维修费用5000元及利息的计算(第584条)。
            当前问题: 房东拒绝支付维修费用，用户询问诉讼流程。"
  
  key_facts: {
    "role": "承租人",
    "contract_type": "房屋租赁",
    "issue": "漏水+维修",
    "repair_cost": 5000,
    "landlord_response": "拒绝支付"
  }
```

## 11. 多 Agent 协作流程

复杂任务可能需要多个 Agent 协作：

```text
用户: "帮我分析这份合同的风险，然后看看类似的判例怎么判的"
↓
Orchestrator Agent
├── 调用 Contract Review Agent → 识别风险条款 + 生成审查报告
└── 调用 Case Analysis Agent → 基于风险条款检索相似判例
↓
Synthesis Agent → 合并两份报告 → 生成综合分析报告
```

## 12. 总结：Agent 设计要点

| Agent | 核心节点 | 关键能力 | 优先级 |
|-------|---------|---------|--------|
| 法律咨询 | Intent → Retrieve → Reason → Cite → Validate | 法条检索 + 法律分析 + 引用校验 | P0 |
| 合同审查 | Parse → Classify → Rule Engine → LLM Review → Legal Retrieve → Template Compare → Report | 双层判断(规则+LLM) + 条款比对 + 法律依据 | P0 |
| 案例分析 | Feature Extract → Multi-path Retrieve → Rerank → Court View Extract → KG Supplement → Synthesize | 要素匹配 + 多路召回 + 裁判趋势分析 | P1 |
| 法条定位 | Intent → BM25 Retrieve → Tree Context → Response | 精确匹配 + 条款树展开 + 版本查询 | P0 |
| 文书生成 | Info Collect → Legal Retrieve → Draft → Cite → Format | 信息收集 + 模板填充 + 法条引用 | P2 |
