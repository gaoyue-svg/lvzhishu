# RAG 设计

## 1. 总体 Pipeline

```text
用户问题
↓
Intent Detect（意图识别 + 法律领域分类）
↓
Query Router（场景路由）
├── 法律问答 → Section 2 (law_qa)
├── 案例分析 → Section 3 (case_analysis)
├── 合同审查 → Section 4 (contract_review)
└── 法条定位 → Section 5 (article_locate)
↓
Query Rewrite（口语化 → 结构化法律查询）
↓
Query Expand（同义词 + 法律概念关联 + 上下位法展开）
↓
Hybrid Retriever（BM25 + Milvus 双路召回）
↓
Merge & Dedup（融合去重）
↓
Rerank（精排 Top8~12）
↓
Context Compression（去噪裁剪 + 引用元数据保留）
↓
Citation Build（构建可追溯的法律引用）
↓
LLM Generate（生成回答）
↓
Citation Validate（引用真实性校验）
↓
Answer（返回 + 保存）
```

## 3. 场景一：法律问答 (law_qa)

### 3.1 Pipeline

```text
用户问题（如："员工被辞退能拿多少补偿？"）
↓
Query Rewrite
  → "劳动合同解除的经济补偿金计算标准、支付条件及违法解除的法律后果"
↓
Query Expand
  → ["劳动合同法第47条", "经济补偿", "N+1", "违法解除", "赔偿金",
     "劳动合同法第87条", "用人单位单方解除", "劳动法"]
↓
Hybrid Retriever
  ├── BM25: 关键词精确匹配 "经济补偿" "劳动合同法"
  │   优势：法条编号精确匹配、法律术语精确匹配
  └── Milvus: 语义检索 "离职补偿" "被开除能拿多少钱"
      优势：口语化表述 → 法律概念映射
↓
Merge → Top20
↓
Rerank：BGE-Reranker 精排
  排序因子：
  - 与改写后查询的相关性（0.4）
  - 法条效力层级（基本法律 > 行政法规 > 司法解释）（0.2）
  - 时效性（现行有效 > 已被修改 > 已废止）（0.3）
  - 文本完整性（完整法条 > 片段）（0.1）
↓
Context Compression → Top8
↓
LLM 生成 + Citation
```

### 3.2 检索参数

| 参数 | 值 | 说明 |
|------|-----|------|
| BM25 Top-K | 20 | 关键词精确匹配 |
| Milvus Top-K | 20 | 语义相似检索 |
| 合并后 Top-K | 20 | 去重融合后 |
| Rerank 后 Top-K | 8~12 | 精排结果 |
| 相似度阈值 | 0.65 | 低于阈值的不返回 |
| Collection 优先级 | law > judicial > case | 法条优先，司法解释补充 |

### 3.3 Query Rewrite 策略（法律问答）

法律用户的口语化程度很高，Query Rewrite 是关键环节：

| 用户原始输入 | Rewrite 后 |
|-------------|-----------|
| "租房漏水房东不管怎么办" | "租赁物维修义务的承担主体、出租人违反维修义务的法律后果、承租人自行维修的费用追偿" |
| "公司不签合同" | "用人单位未订立书面劳动合同的法律责任、二倍工资的计算期间及仲裁时效" |
| "车祸对方全责不赔钱" | "机动车交通事故责任的赔偿范围、侵权人不履行赔偿义务的强制执行程序" |
| "买到假货" | "经营者欺诈行为的认定标准、惩罚性赔偿的适用条件（消费者权益保护法第55条）" |

Rewrite Prompt 模板：

```
你是一个法律查询改写助手。将用户的口语化问题改写为适合法律检索的结构化查询。

要求：
1. 使用法律术语替换日常用语
2. 明确法律关系和权利义务主体
3. 指出可能涉及的法律和条款
4. 保留用户问题的所有核心信息
5. 不要添加用户未提及的事实假设

用户：{user_input}
历史上下文：{conversation_history}

返回改写后的查询：
```

### 3.4 Query Expand 策略

法律领域的同义/关联概念网络：

```text
劳动合同 → 劳动关系、劳务关系、聘用合同、用工协议
经济补偿 → 经济补偿金、赔偿金、代通知金、N+1、2N
违约责任 → 违约金、损害赔偿、继续履行、定金罚则
合同无效 → 合同不成立、合同撤销、合同解除、部分无效
侵权责任 → 过错责任、无过错责任、公平责任、连带责任
```

扩展方式：
1. **法律同义词表**：预构建映射表，检索时注入
2. **Embedding 向量扩展**：用向量相似度找 Top5 相关法条，提取关键词
3. **知识图谱扩展**：查找引用同一法条的相似判例中的关键词
4. **上下位法扩展**：用户问"劳动法"，扩展至"劳动合同法""劳动合同法实施条例"

## 4. 场景二：案例分析 (case_analysis)

### 4.1 Pipeline

```text
用户案情描述（如："甲公司与乙签订供货合同，乙交付货物后甲拖欠货款50万..."）
↓
案例特征提取（LLM + NER）
  ├── 案由：买卖合同纠纷
  ├── 事实要素：供货合同、已交付、拖欠货款、50万
  ├── 争议焦点：货款支付义务是否成立
  └── 主体类型：企业间
↓
多路案例召回
  ├── 案由精确匹配 → case Collection（BM25 筛选案由字段）
  ├── 事实要素向量检索 → case Collection（Milvus 语义相似）
  └── 争议焦点关键词 → case Collection（BM25 关键词）
↓
案例合并 → Top20
↓
案例排序（法律特化 Rerank）
  排序因子：
  - 案由匹配度（0.3）
  - 事实要素重合度（0.35）
  - 法院层级（最高法 > 高院 > 中院）（0.15）
  - 裁判日期（越新越好）（0.1）
  - 地域相关性（0.1）
↓
裁判观点提取 → 每个案例提取：
  - 法院认为部分
  - 适用法条（可链接到法条原文）
  - 裁判结果
↓
知识图谱补充
  - 案例引用的法条 → 展开法条引用链
  - 案例被哪些案例引用 → 影响力分析
  - 相似案例聚类 → 裁判趋势
↓
LLM 综合分析 → 生成案例摘要 + 参考价值评估
```

### 4.3 案例相似度计算

```
案例相似度 = 
  0.35 × 事实要素重合度（关键要素的交集/并集）
+ 0.25 × 案由相似度（案由层级树距离）
+ 0.20 × 适用法条重合度（引用的法条交集）
+ 0.10 × 争议焦点相似度（语义相似度）
+ 0.10 × 裁判结果一致性（支持/驳回/改判的一致性）
```

## 5. 场景三：合同审查 (contract_review)

### 5.1 Pipeline

```text
用户上传合同 + 勾选审查维度（默认全部）
↓
合同解析（Parser Service）
  ├── OCR / 提取文本
  └── 合同条款结构化切分
↓
条款分类
  ├── 当事人信息条款
  ├── 标的/价款条款
  ├── 履行期限/方式条款
  ├── 违约责任条款
  ├── 解除条款
  ├── 争议解决/管辖条款
  ├── 保密条款
  ├── 知识产权条款
  └── 其他条款
↓
逐条款审查（双层判断）
  ┌──────────────────────────────────────┐
  │ Layer 1: 规则引擎（快速筛出明确风险） │
  │  规则示例：                          │
  │  - 违约金 > 实际损失30% → 高风险     │
  │  - 约定"一切损失" → 中风险          │
  │  - 管辖约定"甲方所在地" → 中风险    │
  │  - 未约定解除权 → 提醒               │
  │  - 格式条款排除对方主要权利 → 高风险 │
  │  - 保密期限"永久" → 中风险          │
  └──────────────────────────────────────┘
  ↓
  ┌──────────────────────────────────────┐
  │ Layer 2: LLM 语义分析（深度审查）    │
  │  - 条款是否存在歧义                  │
  │  - 条款是否显失公平                  │
  │  - 条款与法律规定是否冲突            │
  │  - 条款在实务中的常见风险            │
  └──────────────────────────────────────┘
↓
关联法条检索（为每个风险条款找法律依据）
  → 民法典相关条款
  → 司法解释
  → 相似判例（同类型合同纠纷的裁判观点）
↓
条款比对（如果知识库中有同类合同模板）
  ├── 模板条款 vs 实际条款 diff
  ├── 缺失必要条款提醒
  └── 条款偏差度评估
↓
生成审查报告
  ├── 总体风险等级（高/中/低）
  ├── 逐条款风险明细
  ├── 法律依据
  ├── 修改建议（原文 → 修改后 → 理由）
  ├── 合规检查清单
  └── 缺失条款提醒
↓
导出（PDF / Word）
```

### 5.3 合同条款比对

当知识库中有同类合同的标准模板时，进行结构化比对：

```text

第5条 违约责任                第6条 违约责任

   支付违约金                      支付滞纳金

   买方有权解除合同                催告卖方

   卖方全额赔偿
        │                            │
        └──────────┬─────────────────┘
                   ↓
            条款比对结果：
            ├── 利率偏差：日千分之三(109.5%/年) > 法定上限
```

## 6. 场景四：法条定位 (article_locate)

法条定位要求精准、快速，不需要复杂的多路召回：

```text
用户输入（如："民法典关于违约金的规定在哪条？"）
↓
Query Rewrite → "违约金 违约责任 民法典"
↓
BM25 精确匹配（法条定位场景 BM25 优于向量检索）
  - 匹配法条名称 + 条号（如"民法典 第585条 违约金"）
  - 匹配法条内容关键词（如"违约金" "定金"）
↓
Top5 候选法条
↓
Rerank（按版本有效性 + 内容匹配度）
↓
返回：法律名称 → 编 → 章 → 节 → 条 → 款 → 原文
```

## 7. Hybrid Retriever 详细设计

### 7.1 双路召回

```text
查询（Rewritten + Expanded）
        │
        ├─────────────────────┐
        ↓                     ↓
   BM25 检索器            Milvus 检索器
   (Elasticsearch)         (向量数据库)
        │                     │
   ┌────┴────┐           ┌────┴────┐
   │ 关键词    │           │ 语义     │
   │ 精确匹配  │           │ 相似匹配  │
   │          │           │          │
   │ 优势：   │           │ 优势：   │
   │ - 法条编号│           │ - 口语化  │
   │ - 人名地名│           │ - 长文本  │
   │ - 专业术语│           │ - 跨语言  │
   └────┬────┘           └────┬────┘
        │                     │
   Top20 results         Top20 results
        │                     │
        └──────────┬──────────┘
                   ↓
            Merge & Dedup
         （RRF: Reciprocal Rank Fusion）
                   ↓
              Top20~50
```

### 7.2 RRF 融合算法

```
RRF_score(d) = Σ 1 / (k + rank_i(d))

其中：
- d: 文档/chunk
- k: 平滑常数，默认 60
- rank_i(d): 文档在第 i 个检索器中的排名
```

法律 RAG 中可加权的变体：

```
Weighted_RRF(d) = w_bm25 × 1/(k+rank_bm25(d)) + w_milvus × 1/(k+rank_milvus(d))

场景权重分配：
- 法律问答：    w_bm25=0.4, w_milvus=0.6（语义更重要）
- 法条定位：    w_bm25=0.7, w_milvus=0.3（关键词更重要）
- 案例分析：    w_bm25=0.5, w_milvus=0.5（均衡）
- 合同审查：    w_bm25=0.5, w_milvus=0.5（均衡）
```

### 7.3 BM25 分词优化

法律文本的中文分词需要特化词典：

```
默认分词：劳动合同 / 法 / 第 / 四十七 / 条
优化后：劳动合同法 / 第四十七条

需要添加的法律领域词典：
```

## 8. Rerank 法律特化

### 8.1 Rerank 排序因子

```text
Rerank_score = 
  0.40 × 语义相关性（Cross-encoder 打分）
+ 0.15 × 法条效力层级分
       （基本法律=1.0, 行政法规=0.8, 司法解释=0.7, 部门规章=0.6, 地方法规=0.5）
+ 0.20 × 时效性分
       （现行有效=1.0, 已修订(有替代)=0.7, 已修订(无替代)=0.3, 已废止=0.0）
+ 0.10 × 法条完整性分
       （完整法条=1.0, 片段=0.5）
+ 0.10 × 引用频次分
       （在判例中被引用的频次归一化）
+ 0.05 × 文本质量分
       （OCR 质量、格式规范性）
```

### 8.2 Rerank Prompt 模板（LLM-based Rerank 备用）

当 Cross-encoder Reranker 效果不足时，可用 LLM 做精排：

```
你是一个法律检索结果排序专家。根据用户问题，对以下候选法条按相关性从高到低排序。

用户问题：{user_query}

候选法条：
{candidates}  // 每条包含：法条编号、内容摘要、版本、效力层级

排序标准（按优先级）：
1. 是否直接回答用户问题
2. 法条内容与问题的关联程度
3. 法条的效力层级（基本法律优先于行政法规）
4. 法条是否为现行有效版本

返回排序后的法条 ID 列表（Top8）：[id1, id2, ...]
```

### 9.1 引用格式标准

```json
{
  "citations": [
    {
      "id": "cite-001",
      "type": "law",
      "law_name": "中华人民共和国民法典",
      "article": "第585条",
      "paragraph": "第2款",
      "content": "约定的违约金过分高于造成的损失的，人民法院或者仲裁机构可以根据当事人的请求予以适当减少。",
      "version": "20210101",
      "effective_date": "2021-01-01",
      "status": "现行有效",
      "source_document": "中华人民共和国民法典.pdf",
      "chunk_id": "chk-law-001-0585",
      "retrieval_score": 0.92,
      "url": "/document/123/chunk/456"
    },
    {
      "id": "cite-002",
      "type": "case",
      "case_name": "甲公司与乙公司买卖合同纠纷案",
      "case_no": "(2023)闽01民终1234号",
      "court": "福州市中级人民法院",
      "relevant_part": "本院认为，约定的违约金过高，本院酌情调整为...",
      "source_document": "买卖合同纠纷裁判文书.pdf",
      "chunk_id": "chk-case-002-0012"
    }
  ]
}
```

### 9.2 Citation Validator 校验规则

```text
每条引用必须通过以下校验：

1. 来源校验（Source Check）
   □ 引用的 chunk_id 是否存在于检索上下文中？
   □ 引用文本是否与 chunk 原文一致（相似度 > 0.9）？

2. 法条匹配校验（Law-Article Match）
   □ 法律名称 + 条号 是否匹配实际法条？
   □ 如"民法典第585条"确实规定违约金 → 通过
   □ 如"民法典第999条"不存在 → 杜撰，拦截

3. 内容一致性校验（Content Consistency）
   □ LLM 引用的条文内容是否与实际条文一致？
   □ 如 LLM 说"违约金一律无效"但法条说"可以适当减少" → 不一致，标记

4. 版本有效性校验（Version Check）
   □ 引用的法条是否为现行有效版本？
   □ 如引用已被修订的旧版本 → 提示版本风险

5. 幻觉检测（Hallucination Detection）
   □ LLM 是否引用了不存在的法条/案例？
   □ 通过法条编号在数据库中查验证
```

### 9.3 引用校验失败的降级策略

```text
校验失败 → 降级策略
─────────────────────
来源不在上下文 → 删除该引用，重新生成
法条号杜撰    → 删除该引用 + 添加提示"未找到相关法条"
内容不一致    → 替换为原文内容
版本过期      → 保留引用但添加版本提示
孤证（仅1条）  → 添加提示"此观点仅基于单一来源"
```

## 10. 双粒度 Chunk 与检索策略

法律 RAG 需要两种粒度的 Chunk：

```text
┌─────────────────────────────────────────────────────────┐
│                    双粒度 Chunk 策略                      │
├────────────────────┬────────────────────────────────────┤
│   法条级 Chunk      │         段落级 Chunk               │
│  (Article-Level)    │     (Paragraph-Level)              │
├────────────────────┼────────────────────────────────────┤
│ 大小：1条 = 1 Chunk │ 大小：500~1000 tokens             │
│ 内容：完整法条原文   │ 内容：按段落/窗口切分              │
│ 用途：法条定位       │ 用途：语义检索                     │
│      精准引用       │      上下文理解                    │
│      版本管理       │      长文本匹配                    │
├────────────────────┼────────────────────────────────────┤
│ Metadata 示例：      │ Metadata 示例：                    │
│ {                   │ {                                 │
│   "granularity":    │   "granularity":                  │
│     "article",       │     "paragraph",                   │
│   "law_name":       │   "law_name":                     │
│     "民法典",        │     "民法典",                      │
│   "article": "585", │   "article": "585", // 所属法条    │
│   "chapter":        │   "chapter":                      │
│     "合同编",        │     "合同编",                      │
│   "path":           │   "paragraph_index": 2,           │
│     "民法典/合同编/  │   "context_before":               │
│      第八章/第585条", │     "前一段落摘要",                │
│   "version":        │   "context_after":                │
│     "20210101",      │     "后一段落摘要"                 │
│   "status":         │ }                                 │
│     "现行有效"       │                                   │
│ }                   │                                   │
└────────────────────┴────────────────────────────────────┘
```

检索时的粒度选择：

```text
法条定位场景 → 只查 Article-Level Chunk → 返回完整法条
法律问答场景 → 同时查两种粒度
  → 法条级结果：提供精确引用
  → 段落级结果：提供上下文和解释
案例分析场景 → 段落级为主（案情描述），法条级为辅（裁判依据）
合同审查场景 → 段落级为主（条款文本），法条级为辅（合规依据）
```

## 14. 总结：法律 RAG vs 通用 RAG 关键差异

| 维度 | 通用 RAG | 法律 RAG |
|------|----------|----------|
| Chunk 策略 | 固定大小 + 滑动窗口 | 法条级（一条一 Chunk）+ 段落级双粒度 |
| 检索方式 | 单路向量或混合 | 场景路由 + 混合检索 + 权重动态调整 |
| Query 处理 | 简单改写 | 法律术语替换 + 上下位法展开 + 同义词扩展 |
| 排序 | 语义相关性 | 语义 + 效力层级 + 时效性 + 引用频次 |
| 引用 | 可有可无 | 必须精确到条、款、项，可追溯原文 |
| 时效性 | 不敏感 | 法条版本必须可追溯，废止法规需提示 |
| 评估 | 通用指标 | 通用指标 + 引用准确率 + 法条幻觉率 |
| 知识图谱 | 可选 | 强烈建议（引用链、上下位法、判例网） |
| 多租户 | 基本隔离 | 公共法律库共享 + 私有文档严格隔离 |
| 反馈闭环 | 基本评价 | Bad Case 回流 + 黄金 QA 集 + 回归验证 |
