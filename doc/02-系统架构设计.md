## 3. 模块职责

### 3.1 Gateway

- 统一入口，路由分发
- JWT 鉴权拦截，Token 刷新
- 租户上下文注入（从 Token 解析 tenant_id）
- 限流：全局限流 + 按租户限流 + 按接口限流
- 请求/响应日志，脱敏处理
- 跨域配置（CORS）
- 静态资源转发（前端 SPA）
- WebSocket 升级（流式回答推送）

### 3.2 Backend API

- 用户与租户管理（注册、登录、角色、权限）
- 知识库管理（CRUD、启停、权限绑定）
- 文档管理（上传、解析触发、状态查询、删除）
- Chunk 管理（查询、编辑、单条重建向量）
- 会话管理（列表、详情、删除、摘要）
- 消息管理（历史查询、评价反馈）
- Prompt 模板管理（版本化、发布、回滚）
- 模型配置管理（多供应商、多类型）
- 审计日志（操作记录、安全事件）
- 系统配置（全局参数、功能开关）

### 3.3 RAG Service

核心检索增强生成管道：

- **Query Router**：根据意图将请求路由到不同场景 Pipeline（法律问答/案例分析/合同审查）
- **Intent Detect**：识别用户意图类型、法律领域分类
- **Query Rewrite**：口语化查询 → 结构化法律查询，补全上下文
- **Query Expand**：同义词扩展、法律概念关联、上下位法展开
- **Hybrid Retriever**：BM25 关键词 + Milvus 向量混合召回
- **Merge & Dedup**：去重、融合排序
- **Rerank**：BGE-Reranker / Cohere 精排，Top50 → Top8~12
- **Context Compression**：去噪、裁剪、保留引用元数据
- **Citation Build**：构建可追溯的法律引用（法条编号、原文片段、版本号）
- **Citation Validator**：校验引用真实性，防止模型杜撰法条
- **LLM Call**：调用 LLM 生成最终回答

### 3.4 Parser Service

文档解析与结构化处理：

- **文档解析**：PDF / Word / 图片 / HTML / TXT 多格式支持
- **OCR**：扫描件文字识别（支持表格识别）
- **文本清洗**：去页眉页脚、去水印、格式标准化
- **法条结构化解析（Law Structurer）**：
  - 按 "编 → 章 → 节 → 条 → 款 → 项" 构建条款树
  - 每条法条独立索引，保留层级路径
  - 自动识别法条引用（如"依照本法第十二条"）
- **法条版本管理**：
  - 记录生效日期、修订日期、废止日期
  - 支持按时间点检索有效版本
  - 修订前后对比（diff）
- **Chunk 切分**：双粒度策略 — 法条级（一条一 Chunk）+ 段落级（固定窗口）
- **Metadata 抽取**：法律名称、条号、章节、案由、法院、裁判日期等
- **解析任务状态回写**：通过 MQ 通知状态变更

### 3.5 Agent Service

LangGraph 编排的多 Agent 体系：

- **法律咨询 Agent**：面向日常法律问题，返回法规依据、分析过程、风险提示
- **案例分析 Agent**：检索相似案例，提取裁判观点、争议焦点、裁判结果
- **合同审查 Agent**：条款抽取 → 风险识别 → 法规比对 → 修改建议 → 审查报告
- **法条定位 Agent**：自然语言 → 精确法条定位（法律名 + 条号 + 条款内容）
- **文书生成 Agent**：律师函、法律意见书、合同补充条款、风险提示函

每个 Agent 内部包含：
- 意图识别节点
- 检索节点（调用 RAG Service）
- 推理节点（LLM 分析）
- 工具调用节点（MCP 协议）
- 引用校验节点
- Memory 管理节点（法律上下文维护）

### 3.6 Eval Service（检索评估与反馈闭环）

- **在线评估**：实时计算 Faithfulness、Answer Relevancy、Context Precision
- **离线评估**：定期评估 Recall@K、MRR、NDCG
- **黄金问答集管理**：标注的标准 QA 对，按法律领域分类
- **Bad Case 发现**：自动识别低分回答，推送人工复核
- **反馈收集**：用户点赞/点踩、引用准确性反馈、答案有用性评分
- **回流机制**：Bad Case → 人工标注 → 更新 Rerank/Prompt → 回归验证

### 3.7 消息队列（MQ）

选型建议：开发阶段用 Redis Stream，生产环境可迁移到 Kafka。

用途：
- 文件解析任务分发（上传完成 → 触发解析）
- Embedding 任务分发（解析完成 → 触发向量化）
- 合同审查异步处理（大文件耗时较长）
- 检索评估结果回写
- 知识库更新事件通知
- 审计日志异步写入

消息主题设计：

| Topic | 生产者 | 消费者 | 说明 |
|-------|--------|--------|------|
| `document.uploaded` | Backend API | Parser Service | 文档上传完成 |
| `document.parsed` | Parser Service | RAG Service | 文档解析完成 |
| `chunk.embedding.pending` | Parser Service | Embedding Worker | 待向量化 |
| `chunk.embedding.done` | Embedding Worker | Backend API | 向量化完成 |
| `kb.updated` | Backend API | RAG Service | 知识库变更 |
| `eval.badcase.found` | Eval Service | Backend API | 发现 Bad Case |
| `audit.log` | 各服务 | Backend API | 审计日志 |

### 3.8 Storage

| 组件 | 用途 | 法律特化说明 |
|------|------|-------------|
| MySQL | 业务数据、会话、配置、日志、审计 | 法条版本表、合同模板表、案例索引表 |
| Redis | 缓存、任务状态、限流、短期记忆 | 法律上下文缓存、Session Memory |
| 阿里云 OSS | 原始文件、解析结果、导出报告、审查报告 | 按用户/知识库分目录 |
| Milvus | 向量检索 | 按知识类型分 Collection，Partition Key 按租户隔离 |
| BM25 | 关键词检索 | Elasticsearch 或自建，法律术语分词优化 |
| Neo4j | 法律知识图谱 | 法条引用链、上下位法、判例引用网、案由关联 |

## 4. 请求链路

### 4.1 文件入库链路

```text
用户上传文件
↓
Backend API — 创建 document 记录（status=pending）
↓
OSS — 保存原始文件
↓
Backend API — 发送 MQ 消息 (topic: document.uploaded)
↓
Parser Service — 消费消息，开始异步解析
↓
文档解析 (PDF/Word/OCR) + 文本清洗
↓
法条结构化解析（如果是法律法规）
  - 编→章→节→条→款 树形拆分
  - 版本信息提取（生效/修订/废止日期）
  - 法条内部引用识别
↓
Chunk 切分（法条级 + 段落级双粒度）
↓
Metadata 抽取（法律名、条号、案由、法院等）
↓
Parser Service — 写入 knowledge_chunk 表 + 发送 MQ 消息 (topic: document.parsed)
↓
Embedding Worker — 消费消息，调用 Embedding 模型批量向量化
↓
Milvus 写入向量（指定 Collection + Partition Key）
↓
BM25 索引更新
↓
Backend API — 消费完成消息，更新 document 状态
```

### 4.2 问答链路（场景路由）

```text
用户发起提问
↓
Gateway — 鉴权 + 租户上下文注入
↓
RAG Service — Query Router 场景路由
  ├── 法律问答 → law_qa pipeline
  ├── 案例分析 → case_analysis pipeline
  └── 合同审查 → contract_review pipeline
↓
Intent Detect — 意图识别 + 法律领域分类
↓
Query Rewrite — 口语化改写 + 上下文补全
↓
Query Expand — 同义词扩展 + 法律概念关联
↓
Hybrid Retriever
  ├── BM25 Top20（关键词精确匹配）
  └── Milvus Top20（语义相似匹配）
↓
Merge & Dedup — 融合去重 → Top50
↓
Rerank — 精排 → Top8~12
↓
Context Compression — 去噪裁剪
↓
LangGraph Agent — 推理
  ├── 检索上下文注入
  ├── 法律 Memory 注入（跨轮次引用）
  ├── 工具调用（MCP，如法条版本查询）
  └── LLM 生成
↓
Citation Validator — 引用真实性校验
  ├── 引用是否来自检索上下文
  ├── 法条名称与条号是否匹配
  ├── 是否杜撰或幻觉
  └── 失效法规版本风险提示
↓
保存 Message + Citation 到 MySQL
↓
流式返回回答（SSE / WebSocket）
```

### 4.3 合同审查链路

```text
用户上传合同 + 选择审查维度
↓
Parser Service — 合同解析 + OCR
↓
合同条款结构化切分
  - 按条款编号/标题分段
  - 提取：当事人、标的、价款、违约责任、管辖等
↓
条款风险识别（双层判断）
  ├── 规则引擎：预定义风险规则匹配
  │   - 违约金 > 实际损失 30% → 高风险
  │   - 管辖约定不明 → 中风险
  │   - 免责条款过于宽泛 → 高风险
  └── LLM 分析：语义理解补充
↓
相关法规检索（针对每个风险条款）
  - 民法典相关条款
  - 司法解释
  - 相似判例
↓
合同条款比对（如有参考模板）
  - 条款差异检测
  - 缺失条款提醒
  - 条款偏差风险
↓
生成审查报告
  - 风险等级（高/中/低）
  - 风险条款原文 + 分析
  - 法律依据引用
  - 修改建议（原文 → 建议修改 → 理由）
  - 合规检查清单
↓
导出审查报告（PDF / Word）
```

### 4.4 案例分析链路

```text
用户描述案情或输入案由
↓
案例特征提取
  - 案由分类（合同纠纷、侵权、劳动、婚姻家庭...）
  - 事实要素抽取（主体、行为、损害、因果关系）
  - 争议焦点识别
↓
案例检索（多路召回）
  ├── 案由匹配 → 案例库精确检索
  ├── 事实要素 → 向量语义检索
  └── 争议焦点 → 关键词检索
↓
相似案例排序
  - 案由相似度
  - 事实要素重合度
  - 裁判结果相关性
↓
裁判观点提取
  - 法院认为部分
  - 适用法条
  - 裁判结果
↓
法律知识图谱辅助
  - 法条引用链追溯
  - 上下位法关联
  - 同类案例聚类
↓
LLM 综合分析
  - 相似案例摘要
  - 裁判趋势分析
  - 对当前问题的参考价值
  - 风险评估
```

## 5. 多租户数据隔离策略

### 5.1 隔离层次

| 层级 | 组件 | 隔离方式 |
|------|------|----------|
| 业务数据 | MySQL | `tenant_id` 字段 + 查询拦截器自动过滤 |
| 文件存储 | 阿里云 OSS | 按 `bucket/user_id/kb_id/` 路径隔离 |
| 向量检索 | Milvus | Partition Key = `tenant_id`，查询时自动注入 |
| 关键词索引 | BM25/ES | 索引按 `tenant_id` 分片或字段过滤 |
| 缓存 | Redis | Key 前缀 `tenant:{id}:` 命名空间隔离 |
| 知识图谱 | Neo4j | 每个租户独立子图或标签过滤 |
| 会话上下文 | Redis | 按 `tenant_id + user_id + conversation_id` 隔离 |

### 5.2 共享资源

以下资源可在租户间共享（通过配置控制）：

- 公共法律库（民法典、刑法等基础法律）— 所有租户可检索
- 公开判例库（最高法指导性案例）— 所有租户可检索
- Embedding / Rerank 模型实例 — 共享推理服务
- 系统 Prompt 模板 — 按类型共享，租户可覆盖

### 5.3 隔离原则

- 企业上传的私有文档、合同、制度文件 → **严格隔离**
- 企业自建的案例库、知识库 → **严格隔离**
- 公共法律法规、公开判例 → **共享读取**
- 会话和对话记录 → **严格隔离**
- 审计日志 → **严格隔离**，但管理员可跨租户查看

## 6. 法律知识图谱架构（预留）

第一版不强制依赖 Neo4j，但在数据模型中预留图谱接入能力：

### 6.1 实体

| 实体类型 | 属性 |
|----------|------|
| Law（法律） | 名称、颁布机关、生效日期、状态 |
| Article（法条） | 条号、内容、版本、所属法律 |
| JudicialInterpretation（司法解释） | 名称、文号、解释对象 |
| Case（案例） | 案号、案由、法院、裁判日期、裁判结果 |
| Court（法院） | 名称、层级、辖区 |
| CauseOfAction（案由） | 名称、上级案由、所属领域 |
| Clause（合同条款） | 名称、类型、风险等级 |

### 6.2 关系

| 关系 | 说明 | 示例 |
|------|------|------|
| `REFERENCES` | 法条 A 引用法条 B | 民法典第153条 → 民法典第143条 |
| `INTERPRETS` | 司法解释解释某法条 | 合同编司法解释(一)第1条 → 民法典第464条 |
| `APPLIES` | 判例适用某法条 | (2023)闽01民终1234号 → 民法典第584条 |
| `OVERRIDES` | 新法取代旧法 | 民法典第1260条 → 合同法 |
| `AMENDS` | 修订关系 | 刑法修正案(十二) → 刑法 |
| `SIMILAR_TO` | 相似案例 | (2023)闽01民终1234号 → (2023)粤03民终5678号 |
| `SUPERIOR_TO` | 上位法关系 | 民法典 → 合同编司法解释 |
| `BELONGS_TO` | 案由归属 | 买卖合同纠纷 → 合同纠纷 |
| `CONTRADICTS` | 条款与法规冲突 | 合同条款X → 民法典第497条（格式条款无效） |

### 6.3 渐进式接入路径

```text
Phase 1（当前）
  Chunk metadata 中冗余存储实体关系字段
  → 不使用图库，但数据模型支持后期导入

Phase 2（后续）
  导入 Neo4j，构建基础引用关系
  → 法条定位时可展开引用链
  → 案例检索时可追溯适用法条

Phase 3（高级）
  GraphRAG：检索阶段同时查向量库和图库
  → 多跳推理：A法条→引用的B法条→解释B的C司法解释
  → 判例引用网分析：某法条在各地法院的适用差异
```

## 7. 架构原则（修订）

### 7.1 服务解耦
- 后台业务 API 与 RAG 推理服务解耦
- 通过 MQ 实现异步服务间通信
- 各服务独立部署、独立扩缩容

### 7.2 异步优先
- 文件解析、Embedding、合同审查、检索评估使用异步任务
- 消息队列作为服务间通信的默认通道
- 长耗时操作（>5s）必须有异步模式

### 7.3 全链路可追踪
- 知识库 → 文档 → Chunk → 向量记录全链路关联
- 每次检索生成 Trace ID，关联 Query → 召回 → 重排 → 引用 → 回答
- 审计日志覆盖所有关键操作

### 7.4 配置化
- Prompt、模型、Agent、Workflow 尽量配置化
- 支持版本化管理和回滚
- 租户级可覆盖全局配置

### 7.5 可观测性
- 检索链路保留 Debug Trace，便于调优和回放
- 关键指标监控：检索延迟、召回率、引用准确率
- Bad Case 自动发现与回流机制

### 7.6 安全与合规
- 多租户数据严格隔离
- 敏感信息脱敏（合同中的当事人信息、金额等）
- API Key / 模型凭证加密存储
- 法律引用必须可回溯到原文

| 后端框架 | FastAPI | Python 异步，生态成熟 | |
